# Research and design conclusions

Research checked on 3–5 October 2026. Conclusions below distinguish documented capabilities from this project's design choices; published product claims are not a measurement of this implementation.

## TypeSafe Jev

Jev evaluates state with typed Choice, Score and Noul questions. It does not replace a generative planner. This project uses Choice for observation routing and candidate matching. Its adapter uses the documented `POST /v1/systemone` body and validates the returned choice and probabilities. [TypeSafe introduction](https://docs.typesafe.ai/introduction), [HTTP API](https://docs.typesafe.ai/api).

TypeSafe's confidence summarizes an answer distribution. A threshold is a routing decision and is not a proof of correctness or user authorization. The default 0.8 threshold is a starting configuration, not an experimentally calibrated browser threshold. [TypeSafe confidence](https://docs.typesafe.ai/confidence).

Our proposed extension is a hybrid: an LLM plans, Jev makes narrow decisions, ordinary code validates and executes. Whether this is better than LLM-only browsing must be tested with equal task budgets and the same planner.

## Chrome control

Chrome's debugger API exposes a subset of DevTools Protocol domains, including Input, Runtime, DOM, Page and Accessibility. It supports tab attachment and frame sessions, but enterprise restrictions can prevent attachment. This enables trusted input and viewport capture; it does not provide unrestricted control of Chrome or the OS. [Chrome debugger API](https://developer.chrome.com/docs/extensions/reference/api/debugger).

Manifest V3 workers can stop when idle. Chrome documents WebSocket traffic and active debugger sessions extending worker lifetimes; durable state should still use storage. This project combines session storage, heartbeat traffic and reconnect alarms. [Worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle).

An isolated DOM script can observe normal controls without mixing the extension's privileged state into the page. The side panel is the user's place to grant access and monitor tasks. [Content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts), [Side Panel API](https://developer.chrome.com/docs/extensions/reference/api/sidePanel).

Store distribution needs a separate policy review, particularly the advanced JavaScript-evaluation tool and any future remote instructions interpreted as code. The bundled extension loads its executable assets locally. [Chrome remote-code policy guidance](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code).

## LLMs and MCP

Both OpenAI and Anthropic document a tool-call / execute / tool-result loop. Responses reasoning output must remain in conversation state; Anthropic tool results need their matching tool-use IDs and correct placement. Provider adapters preserve those differences instead of pretending every endpoint has one wire format. [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling), [Anthropic tool-call handling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls).

The official MCP SDK handles initialization, schema/tool registration and stdio transport. Tool annotations describe the tools to clients, while enforcement lives in the bridge and extension. Direct tools allow a host model to operate the browser; task tools separately expose the bridge's planner. [MCP SDK server documentation](https://ts.sdk.modelcontextprotocol.io/server).

Local MCP registration is supported in local Codex clients. Hosted chats use different connection mechanisms, so creating or registering a local server does not establish that this conversation has it in its live tool catalog. The shipped CLI helper is a tested local MCP client. [Official client MCP configuration](https://learn.chatgpt.com/docs/extend/mcp).

## Path to the reference product

Anthropic describes Claude in Chrome as a browser assistant and emphasizes prompt-injection defenses. Matching its product requires repeated real-task evaluation, handoffs and operational reliability in addition to input APIs. We have not reverse-engineered Claude or measured parity. [Claude in Chrome](https://claude.com/blog/claude-in-chrome-generally-available), [Anthropic browser prompt-injection research](https://www.anthropic.com/research/prompt-injection-defenses).

BrowserGym provides a framework spanning MiniWoB, WebArena, VisualWebArena and WorkArena. These are candidate benchmarks for a separate evaluation harness; the current extension suite uses deterministic local fixtures. [BrowserGym project](https://github.com/ServiceNow/BrowserGym).

## Layers beyond screenshots and DOM

Google's Chrome DevTools MCP tool reference covers navigation/input, console and network investigation, performance and emulation. Microsoft Playwright MCP emphasizes structured observations and includes tab and storage-oriented tools; its companion CLI publishes a workflow skill. These sources informed the layered vocabulary here. They do not establish that every listed upstream tool is present in this extension. [Chrome DevTools MCP tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md), [Playwright MCP](https://github.com/microsoft/playwright-mcp), [Playwright CLI workflow skill](https://github.com/microsoft/playwright-cli/blob/main/skills/playwright-cli/SKILL.md).

The implemented layers are DOM refs, viewport images/native input, bounded main-frame accessibility, DevTools console/network metadata, gated response bodies, performance metrics and viewport emulation. Multi-tab work uses explicit independent batches and per-tab queues. The scheduler is this project's design: dependent actions must remain sequential, and browser writes are never speculatively retried. Nested cross-process frame input is now implemented and stress-tested for supported layouts. Full trace capture, request interception, storage mutation, broader emulation and child-target diagnostic session mapping still need separate scope and tests.

Chrome documents navigation history entries and history-entry navigation in Page CDP. The extension uses these to inspect and authorize the history destination before moving, and waits for a committed document. This also fixed an integration failure encountered with background-tab history. [Page protocol](https://chromedevtools.github.io/devtools-protocol/tot/Page/).

The installed WebMCP skill distinguishes exposing a website's intentional agent actions from automating arbitrary browser pages. We read it for this distinction. We have not exposed new tools on third-party websites or claimed WebMCP support; native website-tool discovery is a future, capability-detected layer rather than a replacement for the extension's external MCP.

## Long sessions and explicit memory

OpenAI documents manual `/responses/compact` and server-managed compaction. Manual compaction returns canonical output for subsequent requests; its entire result must be retained, including opaque items. This project implements optional manual compaction and a provider-neutral summary fallback. It does not implement server-managed compaction. [OpenAI compaction](https://developers.openai.com/api/docs/guides/compaction).

Conversation persistence and reusable fact storage are separate design choices. The user selected conversation history plus explicitly saved reusable facts. Consequently, transcript/checkpoint storage is automatic within a conversation; cross-conversation facts are written only through the panel or explicitly requested MCP memory operations. Permissions are never remembered as authorization. Fresh observations after restart and explicit unknown-outcome records matter because browser state can change independently of model memory.

## Native tab groups

Chrome exposes native group creation and membership through `chrome.tabs.group`/`ungroup`, with group title, color and collapse state in `chrome.tabGroups`. The latter requires the `tabGroups` manifest permission. Group IDs are unique within a browser session, so the extension stores its per-window reuse map in session storage and verifies the group still exists. [Chrome tab groups](https://developer.chrome.com/docs/extensions/reference/api/tabGroups), [Chrome tabs](https://developer.chrome.com/docs/extensions/reference/api/tabs).

The primary-source review suggested three practical priorities: reduce unnecessary model context/turns, verify outcomes independently, and retain execution uncertainty across sessions. The release implements the browser/transport portions and creates measurement hooks for the model portion. Jev confidence is still uncalibrated against the browser corpus.

## Input latency and rendering evidence

Puppeteer's CDP mouse implementation maintains explicit pressed-button state. This informed matching mouse down/up flags in our native input sequence. [Puppeteer input implementation](https://raw.githubusercontent.com/puppeteer/puppeteer/main/packages/puppeteer-core/src/cdp/Input.ts).

Chromium's input handler routes mouse events through asynchronous widget hit testing; wheel events explicitly synchronize visual state. Chrome also documents reduced background scheduling, although the older timer article does not by itself explain the observed modern click delay. Our compositor/scheduling explanation is an inference from these sources and fixture experiments, not an established upstream bug diagnosis. [Chromium input handler](https://raw.githubusercontent.com/chromium/chromium/main/content/browser/devtools/protocol/input_handler.cc), [Chrome background policy overview](https://developer.chrome.com/blog/background_tabs/).

A discarded screenshot before framed input, followed by fresh geometry, removed the observed missed-click failure in two 100-frame runs. A global background screenshot experiment increased overhead without reducing tail latency, so it was removed. Foreground activation through the existing Chrome tab API reduced the matched fixture click p95 from 1,028 ms to 29 ms; browser_step now exposes an explicit foreground option for sequential visible work. No mutation is repeated to hide a failure.

## Screenshot and polling decisions in 0.3.0

The named Page.captureScreenshot API provides PNG/JPEG format and JPEG quality controls. We expose those choices while retaining PNG as the default. Text-heavy and image-heavy fixtures are measured separately because compression benefits depend on content. Images retain their MIME type in the MCP and provider transports. [Page protocol screenshot method](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-captureScreenshot).

Chrome's scripting API evaluates isolated functions and awaits returned promises. A long-lived page-side waiter would therefore need a separate cancellation, navigation and background-timer design. This optimization retains bounded worker polling with faster early probes and backs off for longer waits; each probe revalidates access and document state. It does not claim event-driven DOM observation. [Chrome scripting API](https://developer.chrome.com/docs/extensions/reference/api/scripting).
